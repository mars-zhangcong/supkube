## 一、执行摘要

两份新 PRD 整体质量很高，尤其工程诚实度突出：PRD-005 明确不把 SSE Live Tail 吹成秒级、AI 根因一律标注置信度、采用 5 phase 分批 ship；PRD-006 直接点破「Velero CR 没有原生 step phase，必须合成」并设了 Phase 0「verify-before-architect」实测门禁、阶段推不出时降级为 `unknown` 而非假装绿色。这种「不过度承诺 + 先实测再架构」的纪律，是这套文档最值得保留的特质。

放行前需处理的问题集中在三类：(1) 两份 PRD 之间的 **deep-link 契约实际不一致**（都声称已对齐，参数名 / 路由却不同）；(2) **ADR-033 编号撞车**（被 PRD-003/004 与 PRD-005 分别指向两件不同的事）；(3) **SSE 在 PRD-005 重新出现，与团队自己的 ADR-015「因 nginx ingress 兼容性不用 SSE」冲突**，需要正面解决而非默默绕过。此外，AI 根因 / 排错把日志与错误外发给 LLM，应统一纳入首份报告 T4 的数据出境治理（日志比元数据更可能含密钥 / PII）。

### 放行结论速览

| PRD | 结论 | 前置条件 |
|---|---|---|
| **PRD-005** Log Viewer v2 | 有条件通过（按 phase ship） | 统一 deep-link 契约（与 PRD-006）；解决 SSE 与 ADR-015 冲突（写明 nginx ingress 配置）；修复 ADR-033 编号撞车；澄清审计导出依赖 forwarding / pod 日志存活；AI 根因外发纳入 T4 治理 |
| **PRD-006** Activity Timeline | 通过（Phase 0 门禁已内建） | 与 PRD-005 统一 deep-link 契约；ETA 承诺取舍；约束 ListActions 预聚合成本；AI 排错 tab 外发纳入 T4 治理 |

**严重度图例**：Blocker（进研发前必解）/ High（影响正确性·合规·跨 PRD 契约）/ Med（可维护性·性能·体验）/ Info（文档卫生）。

## 二、跨 PRD / 跨文档顶层问题

### X1（High）PRD-005 与 PRD-006 的 deep-link 契约实际不一致

两份 PRD 都声称 deep-link「已对齐」，但写出来的协议对不上：

| 维度 | PRD-005 §4.8 | PRD-006 §4.6 |
|---|---|---|
| 基础路由 | `/logs?...` | `/observability?tab=logs&...` |
| 时间窗参数 | `since=1h`（带单位字符串） | `sinceSeconds=600`（纯秒数） |
| 跳行参数 | `line=4421`（数字） | `scrollToLine=auto`（数字或 `auto`） |
| 其它 | `verbosity` / `t` / `live` / `tail` / `severity` | 仅 component / grep |

这不是措辞差异，而是**会直接让跳转失效的契约错位**：PRD-006 点「查看日志」拼出的 URL，PRD-005 的解析器不认识 `sinceSeconds` / `scrollToLine`，也不在 `/observability` 路由下。建议：把 deep-link query-param schema 抽到**单一来源**（一个小 ADR 或 PRD-005 §4.8 作为权威，PRD-006 引用而非另写），明确路由、参数名、取值格式、`auto` 语义，两边都对它写验收。

### X2（High，文档）ADR-033 编号撞车

- PRD-003 / PRD-004：`ADR-033（拟）= AI Advisor 架构`
- PRD-005：`ADR-033（拟）= 结构化日志规范 + 错误代码体系`

同一个 ADR 号被指向两件完全不同的架构决策。等到真去写 ADR-033 时必然冲突。建议立即重编号（例如 AI Advisor = ADR-033，结构化日志 = ADR-035），并在 PRD 索引里统一引用。顺带建议维护一张 ADR 号台账，避免后续 PRD 继续撞号（目前 ADR-032~034 都还是「拟」，正是混乱高发区）。

### X3（High）SSE 在 PRD-005 重新出现，与 ADR-015 冲突；与 PRD-004 一起需要项目级口径

架构设计.md 的 **ADR-015** 明确写过「不用 WebSocket / SSE：复杂度↑，K8s nginx ingress 兼容性问题」。但 PRD-005 §4.3 用 SSE 实现 Live Tail，PRD-004 也用 SSE 做 MCP 传输。两处都在不引用 ADR-015 的情况下重新选了 SSE。

需要区分对待，而不是一刀切：

- **PRD-005 Live Tail 用 SSE 是合理的**（这是真正的 server→client 单向流，正是 SSE 的适用场景）——但必须正面解决 ADR-015 记录的 ingress 问题：nginx ingress 默认会缓冲响应体，会让 SSE「攒一批才吐」甚至超时断开。落地时需在 DoD 里固化 ingress 配置（如 `nginx.ingress.kubernetes.io/proxy-buffering: "off"`、加大 read/send timeout、`X-Accel-Buffering: no` 响应头），并实测验证逐行到达。
- **PRD-004 MCP 传输不该用 SSE**（见首份报告 T2：MCP 已弃用 SSE，改 Streamable HTTP）。

建议用一份 ADR 统一「长连接 / 流式传输在 SupKube nginx ingress 后的官方做法」，让各 PRD 引用，而不是每份 PRD 各自重新决定 SSE。

### X4（High）AI 根因 / 排错把日志与错误外发 LLM，需并入首份报告 T4 治理

PRD-005 §4.9（最近 100 行日志 → `/advisor/log-rootcause`）和 PRD-006 §4.7（stages + errorMessage + 关联资源 → `troubleshoot.tmpl`）都把运行时数据喂给 LLM。**日志比元数据更危险**——堆栈、连接串、token、PII 经常出现在日志里。这必须复用首份报告 T4 的结论：默认本地 / 最小外发、脱敏在 logger 一侧（PRD-005 §7 已有 Secret 脱敏中间件，应作为 LLM 外发前的强制前置）、SECURITY.md 增设 AI 数据处理专章、ADR 固化。PRD-005 §4.9「裁剪 + 脱敏」的承诺要落到与 §7 脱敏中间件同一条管线上，而非各做一套。

## 三、逐份评审

### PRD-005 — Log Viewer v2

亮点：工程诚实（SSE 延迟、AI 置信度、分批 ship）、RBAC 后端过滤、Secret 脱敏在 logger 一侧、Virtual Scroll DOM 上限量化。

| # | 严重度 | 问题 / 风险 | 建议改法 |
|---|---|---|---|
| 1 | **High** | SSE Live Tail（§4.3）与 ADR-015 冲突；nginx ingress 默认缓冲会破坏逐行流式。 | 见 X3：DoD 固化 ingress 配置（proxy-buffering off / timeout / X-Accel-Buffering），并实测逐行到达延迟。 |
| 2 | **High** | 审计 / 合规导出（US 3.3、DoD #20）依赖实时 pod 日志，但 PRD 自己声明「不做长期存储」。几天前失败的备份其 Pod / 容器日志可能已被 kubelet 轮转或随 Pod 删除而消失，导致合规导出取不到。 | 明确：审计导出仅在「已配置 Forwarding 到客户日志平台」或「pod 日志仍存活」时有效；US 3.3 应改写为「通过 Forwarding 落到客户平台后由其保留」，不要让客户以为 SupKube 自身可回溯任意历史。 |
| 3 | **Med** | 多 pod 同名「并行 stream + 按 timestamp 1s 窗口合并」（§4.3）。容器日志时间戳来自各节点 runtime，跨节点不保证单调 / 同步；1s 窗口仍可能错序或漏掉迟到行。`GetLogs(Follow)` 每流占一条 apiserver 长连接 + goroutine，多 viewer × 多 pod 会压 apiserver。 | UI 标注跨 pod 顺序为「尽力而为」；对每连接的 pod 数 / 总并发 SSE 设上限（NFR 已有 active connections 指标，应配额化）；合并窗口可配置并说明取舍。 |
| 3 | **Med** | err_code 体系（§4.5）+ 三层日志（§4.4）依赖未写的 ADR-033，且要改造 backend/agent/operator 三套 logger（v2.2，1.5-2 周）。跨切面大改、又卡在「拟」状态的 ADR 上。 | 先把 ADR-033（重编号后）评审通过再开 v2.2；err_code 首批 20 个单独 task 梳理（Q5 倾向正确）；旧组件兼容期 ≥ 6 个月（Q4）写进 ADR 迁移路径。 |
| 4 | **Med** | Minimap（§4.6）对 10 万行渲染标记，若逐行 1px 直接画会有性能 / 视觉问题。 | Canvas 渲染 + 按视口高度分桶聚合（每像素聚合该区间最高 severity），而非逐行 1px。 |
| 5 | **Med** | AI 根因外发日志（§4.9）。 | 见 X4：经 §7 脱敏管线 + T4 出境治理；置信度阈值 0.5（Q8）待真实数据校准，先标「实验性」。 |
| 6 | **Info** | Deep-link 参数与 PRD-006 不一致。 | 见 X1：统一 schema，本 PRD §4.8 适合作为权威来源。 |

### PRD-006 — Activity Task Detail Timeline

亮点（少见的好）：诚实标注 Velero 无原生 step phase；Phase 0 verify-before-architect + 真实 CR fixture 入库；推不出的阶段降级 `unknown` 不假装绿色；列表卡片预聚合避免 per-card 调用。

| # | 严重度 | 问题 / 风险 | 建议改法 |
|---|---|---|---|
| 1 | **High** | 与 PRD-005 的 deep-link 契约不一致（§4.6 路由 `/observability?tab=logs`、参数 `sinceSeconds` / `scrollToLine`）。 | 见 X1：改为引用 PRD-005 §4.8 权威 schema，对齐路由与参数名，并写进 DoD #10/#11。 |
| 2 | **Med** | 合成层跨 Velero 版本（1.11~1.14）字段 / 时序差异。PRD 已用 Phase 0 fixture + unknown 降级缓解（很好），但缺版本兼容矩阵与回归机制。 | 显式列「已测 Velero 版本」矩阵；把 fixture 做成 CI 契约测试，按支持版本各跑一遍；新版本上线前刷新 fixture。 |
| 3 | **Med** | US 3.1 承诺「估算剩余 5min」，但 API schema 无 `etaSec` 字段，DoD 也未含 ETA。备份 ETA（尾部对象 + Finalize）极不准。 | 要么补 `etaSec` 并标注「粗略估算」，要么从 US 删掉 ETA 承诺，避免做出来不准被吐槽。 |
| 4 | **Med** | ListActions 预聚合 4 字段（§4.3）意味着每次列表请求都要对运行中 action 合成阶段、读多个子 CR。运行中 action 多时成本放大，NFR 的 ListActions P95 ≤ 1.2s 可能破。 | 预聚合仅对 running action 执行、终态缓存；分页设每页 action 上限；子 CR 读取加并发上限与缓存。 |
| 5 | **Med** | AI 排错 tab（§4.7）外发 stages + errorMessage + 关联资源。 | 见 X4：纳入 T4 出境治理；仅终态 failed/partial 显示（Q8 正确）。 |
| 6 | **Info** | hover 卡（§4.5）暴露 Node Agent Pod IP / Volume URN / Resource ID 等内部信息，viewer 即可见（§7）。 | 对运维工具可接受；但 `detail=full` 的基础设施细节可考虑要求更高权限，至少在文档里注明这是有意的信息披露。 |

## 附录：技术核实要点

- Velero `Backup`/`Restore` CR 顶层仅有粗粒度 `.status.phase`，无原生 step-by-step 阶段；细粒度需从 `DataUpload`/`DataDownload`/`PodVolumeBackup`/`VolumeSnapshot` 等子 CR 的 `.status` 合成——PRD-006 已诚实标注，做法正确。
- Velero DataUpload/DataDownload `.status.progress`（totalBytes / bytesDone）可作为真实进度来源（PRD-006 Q3 选「优先真实字段」正确）。
- nginx ingress 默认对响应体做缓冲，会破坏 SSE 逐行流式；需 `proxy-buffering: off`、加大 read/send timeout、`X-Accel-Buffering: no`——这是 ADR-015 当年顾虑的工程解法，应写进 PRD-005 DoD。
- `kubectl logs --follow`（client-go `GetLogs(Follow:true).Stream`）每流占一条 apiserver 长连接 + goroutine；高并发需配额与连接生命周期管理（PRD-005 §4.3 已写 ctx cancel / 30min reconnect，方向对，需补每连接 pod 数 / 总并发上限）。
