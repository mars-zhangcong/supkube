## 一、执行摘要

两份 PRD 一重一轻、都很扎实。

**PRD-008** 的根因判断是这套文档里最关键的一次纠错：它指出 SupKube 的 Activity 列表一直是"从 Velero CR 实时派生的 view"而非持久化 audit log，所以 RP 一删 Activity 那行就消失（Mars 实测"删完 5 个 RP 后 Activity 全空"的真因）。修复方向（独立 audit event 流 + ListActions 改 `union(CR 实时视图, 事件历史视图)`）正确，且把自己定位为 **PRD-006 Activity Timeline 的数据层基石**——这个定位是对的，PRD-006 的 Timeline / Log 跳转 / AI 根因确实"没有持久化就是空中楼阁"。Force Delete 的副作用治理（BSL 不清 + backup-sync 60s 重建 + 历史孤儿）也抓得准，改名 "Force Delete → Force Strip Finalizer" 很诚实。**需要在研发前定的，集中在 audit 存储选型与"不可篡改"的真实实现，以及孤儿清理对 Kopia 共享仓库的安全性。**

**PRD-009** 是低风险的 UI 词汇重构：把自创的 L1/L2 互斥按钮改成 Kasten 风格的 "Snapshot 默认 + Enable Backup via Snapshot Export 开关 + 选 BSL"，**后端数据模型 / Velero Schedule / policypair controller / `supkube.io/dual` annotation 零变更**，0 迁移风险，scope 克制。只有几处语义澄清和跨 PRD 术语一致性要处理。

## 二、PRD-008 评审

### D1（High）audit event 存储选型：CRD-on-etcd 在规模下是反模式，且与 ADR-019 既有审计未对账

§4.1.2 三选一预倾向 **B（独立 CRD）**，Phase 0 测 1 万 event。两个问题：

1. **etcd 不是为高写入 append-only 审计流设计的**。审计事件每个 Task ≥ 5 条，乘以"多 ns × 每小时备份 × 6 种 ActionType × 90–180 天保留"，真实上限远不止 1 万——可能十万到百万级。CRD 对象全进 etcd，与**集群真实状态共享同一 etcd 配额**（默认 2–8GB），逼近配额时 etcd 整体性能劣化、甚至威胁集群稳定；apiserver 的 list/watch 与 informer 首次 list 的内存也随对象数线性增长。"把审计日志塞进 etcd" 是社区公认的反模式。Phase 0 只测 1 万 + list 延迟不够，应测**现实上限（如 180 天满负载）+ etcd 容量/压力影响**。
2. **与 ADR-019 未对账**：ADR-019 已确立"审计日志 = K8s Events + stdout 双写"。PRD-008 又引入一套 audit event 流——这是取代 ADR-019、还是并存？两套审计语义/保留/查询不一致会让合规审计无所适从。

**建议**：(a) 对 append-heavy 审计流，倾向 **Option C 嵌入式存储（SQLite/BoltDB on PV）**，把审计数据移出 etcd；CRD 仅在"事件量可证明有界且低"时才选。(b) Phase 0 增"现实上限 + etcd 影响"测试维度。(c) 在拟 ADR-037 里显式写清与 ADR-019 的取代/并存关系，并登记进 ADR 号台账。

### D2（High）"不可篡改 audit" 需要真实强制机制，不能靠"immutable annotation"

§7 称 "event chain 不可篡改（CRD 用 immutable annotation / store 用 append-only）"。但 **CRD 上的 "immutable annotation" 不构成不可篡改**——任何有该 CRD edit RBAC 的主体都能改对象；真要不可变需 **validating admission webhook 拒绝 update**，或 **hash-chain（每条 event 链入前一条的 hash）**，或写入 **WORM/外部 append-only 存储**。对一个面向 SOC2/等保的合规取证特性，"约定式不可变" 不够。

**建议**：明确 tamper-evidence 机制——嵌入式存储走严格 append-only + 周期性 hash-chain 校验；若用 CRD 则配 admission webhook 禁 update/delete（TTL 清理走特权 ServiceAccount）。把"如何证明没被篡改"写进 DoD。

### D3（High，DR 特性反身性）多集群审计：事件存在工作集群 etcd 里，集群损毁时审计随之消失——恰恰是最需要它的时刻

`ClusterID` 字段表明多集群。若 audit event 是各**工作集群**自己 etcd 里的 CRD，那么当一个集群在灾难中损毁时，它的审计历史也一起没了——而灾备产品的审计取证恰恰在"集群挂了之后"最关键。S3 合规场景 "3 个月后查到该 Backup 执行过" 也要求审计在 RP/集群消失后仍可达。

**建议**：审计事件应能**脱离单工作集群存活**——写入管理集群（若有 MCM/控制面），或周期性归档到 BSL（与备份同源的对象存储，天然异地），作为集群损毁后的取证副本。至少在 PRD 里把"审计存活边界"讲清（当前设计在集群损毁后是否还查得到）。

### D4（Med）删除锁定状态应由 Task/审计状态驱动，而非重新去 list DBR

§4.3.1 用 "list DBR 看有无 active phase" 判定 `deletionState`。但 PRD 自己在 Goal 里就点了"历史 12 个老 DBR 残留陷阱"——**陈旧 DBR 会造成误判**（假"删除中"），或 DBR 已 Processed 但 CR 未 GC 时漏判。既然本 PRD 正在建 Task/event 模型，`deletionState` 应直接来自"该 RP 是否有一个 active 的 DeleteBackup Task"，而不是再从 DBR 反推。

**建议**：`deletionState` 取自 audit Task 状态（本 PRD 的权威数据源），DBR 仅作执行细节；避免与已知的"残留 DBR"问题耦合。

### D5（High）孤儿清理的 `mc rm backups/<name>/` 对 Kopia 共享仓库不完整/危险（与 PRD-007 P1 同源）

§4.4.2 孤儿清理列出 `mc ls minio/backups/` 与 CR 做 diff，清理给 `mc rm --recursive minio/backups/<name>/`。但（与 PRD-007 P1 同一事实）**Velero 的卷数据不在 `backups/<name>/` 下，而在按 ns 共享去重的 `kopia/<ns>/` 仓库里**：

- `mc rm backups/<name>/` 只删了**备份元数据**，该备份的**卷数据块仍留在 kopia 仓库**（变成更深一层的孤儿，只能靠 Kopia 维护/GC 回收）。
- 若试图直接 `mc rm` kopia 仓库对象，会因 dedup **破坏同 ns 其它备份**。
- 真正干净的删除是 Velero 的 DBR 流程（它驱动 Kopia 仓库维护），而非裸 `mc rm`。

**建议**：孤儿清理区分两类——(a) 纯元数据孤儿（无对应 kopia 数据）可安全删 prefix；(b) 带数据的孤儀需走"重建最小 Backup CR → DBR 删除"或 Velero/Kopia 仓库维护，**不可裸 mc rm 整个 prefix**。文案/命令要按类型给，否则会教客户删出"半个备份 + 永久残留数据块"或损坏共享仓库。与 PRD-007 P1 合并出一份"BSL 数据正确删除"的统一指引。

## 三、PRD-009 评审

低风险 UI 词汇重构，0 后端变更，向后兼容、i18n 兼容期、audit 双写、CI lint 禁旧 key 都是好做法。以下为澄清项。

### E1（Med）先厘清 SupKube 的 "Snapshot" 到底是什么，再决定能否套 Kasten 词

§4.1 写默认 Snapshot 的 BSL = `local-store`，并括注"**CSI snapshot 或 in-cluster MinIO**"——这两者是 ADR-031 里**完全不同的两层**：Layer 1（CSI VolumeSnapshot，存储层快照，秒级、原地、不拷数据）vs Layer 2（本地 MinIO BSL，Velero 备份，分钟级、拷数据）。Kasten 的 "Snapshot" 明确是**存储层快照**（instant，再 export 成 "Backup"）。若 SupKube 的 "Snapshot" 实际是"备份到本地 MinIO"，把它叫 "Snapshot" 反而会**误导从 Kasten 迁来的客户**（他们以为是秒级原地快照，结果是较慢的数据拷贝）。

**建议**：§4.1 去掉 "CSI snapshot 或 in-cluster MinIO" 的二义，明确 "Snapshot 动作" 对应 ADR-031 哪一层；只有当它确为 Layer 1 存储快照时，Kasten 词汇映射才诚实。若它其实是本地 BSL 备份，需在 hint 里讲清，避免反向认知错位。

### E2（Med，可能 High）"Snapshot 始终开、不可取消" 在无快照能力的集群上不可满足

§4.1 + Q4 把 "Action: Snapshot" 设为固定不可取消。但若目标集群**没有 CSI 快照能力**（无 VolumeSnapshotClass / 存储不支持快照 / 纯文件级备份场景），强制 "Snapshot 永远开" 就**无法满足**——这类环境唯一可行的保护恰恰是 Export/Backup-only。而且核实 Kasten 实际行为：Kasten 本身支持 **"Export Snapshot References Only"（仅元数据）** 这类不抓数据快照的模式，PRD-009 把 "Metadata-only" 推到 v1.x（Q4），这与"对齐 Kasten"目标本身有 parity gap。

**建议**：v1 至少处理"集群无快照能力"的退化路径（允许 Export/Backup-only），UI 在检测不到 VolumeSnapshotClass 时不要强制 Snapshot-always-on；把 "references-only / metadata-only" 的 Kasten parity 缺口在 Out-of-Scope 里诚实标注为"暂不完全对齐"。

### E3（Low）Kasten 实际措辞微调（回答 Q1）

核实 Kasten K10 官方用词：开关是 **"Enable Backups via Snapshot Exports"**（复数 Backups / Exports），导出目标称 **"Export Location / Location Profile"**（不是 "Storage"），且有 **"Export Snapshot Data" vs "Export Snapshot References Only"** 之分。PRD-009 现用 "Enable Backup via Snapshot Export"（单数）+ "Snapshot Export Storage"。

**建议**：i18n 英文键尽量贴官方（"Enable Backups via Snapshot Exports" / "Export Location"），最大化 Kasten 迁移客户的 0 学习成本——这正是本 PRD 的立项目标。

### E4（Med，跨 PRD 一致性）Policy 去掉 L1/L2，但 PRD-007 的 Posture 卡仍是 L1-L5

PRD-009 把 Policy UI 的 L1/L2 词汇移除，改 Snapshot/Export；但 PRD-007 §4.8 的 "数据韧性 Posture" 卡仍展示 "L1 本地快照 / L2 本地 BSL / L3 云 BSL / L4 / L5"。结果同一产品里 Policy 面说 Snapshot/Export、Dashboard 面说 L1-L5，客户会困惑二者关系。

**建议**：两条轴本可并存（Policy 动作词汇 vs 3-2-1-1-0 韧性层模型），但要**显式定义并在 UI 上打通**——例如 Posture 卡每层标注它对应的 Policy 动作（L1=Snapshot，L2/L3=Snapshot Export 到本地/云 BSL）。在 PRD-009 或 PRD-007 里加一句术语映射表，避免两套词各说各话。

### PRD-009 其它（Info）

- 向后兼容、i18n 兼容期 1 版本、audit 双写（`policy.tier` + `policy.export_enabled`）、CI lint 禁旧 key——都很稳妥，无异议。
- a11y（Snapshot disabled-but-checked 的 ARIA）考虑到位，赞。

## 四、跨 PRD / 跨 ADR 一致性

- **PRD-008 ↔ PRD-006**：PRD-008 自我定位为 PRD-006 的数据层基石，正确。**排期含义**：PRD-006 中依赖"已删除 RP 仍可见 / AI 根因有历史可学"的部分，应在 PRD-008 audit 持久化落地后再做，否则 PRD-006 的 Timeline 对已删 RP 仍是黑屏。建议把 PRD-008 Phase 1（audit 持久化 + ListActions union）设为 PRD-006 对应 phase 的前置。
- **PRD-008 ↔ PRD-007（P1）**：孤儿清理与 Layer 4 复制是**同一个 Kopia 共享仓库事实**的两面。建议合并出一份"BSL 数据正确删除 / 复制"统一技术指引，供两份 PRD 引用，避免各写一套裸 mc 命令。
- **PRD-008 ↔ ADR-019 / ADR-035 / 拟 ADR-037**：与 ADR-019 既有审计的取代/并存要在 ADR-037 讲清；ErrorCode 沿用 ADR-035（已正确引用）；ADR-037 登记进台账。
- **PRD-009 ↔ PRD-007**：术语轴一致性（E4）。
- **PRD-009 ↔ ADR-025/026**：明确不动 dual-schedule + policypair controller，0 风险，正确复用。

## 附录：技术核实要点

- **Kasten K10 术语**（回答 PRD-009 Q1）：策略开关为 "Enable Backups via Snapshot Exports"；导出目标为 "Export Location / Location Profile"；区分 "Export Snapshot Data"（含数据）与 "Export Snapshot References Only"（仅元数据）。Kasten 的 Snapshot=存储层快照，Backup=导出后的对象存储副本。
- **etcd 作审计存储**：etcd 有容量配额（默认 2–8GB）且与集群状态共享，不适合高写入 append-only 审计流；大量 CRD 对象损害 apiserver list/watch 与 informer 内存。
- **Velero/Kopia 删除**：卷数据在按 ns 共享去重的 `kopia/<ns>` 仓库；裸 `mc rm backups/<name>/` 只删元数据，数据块需 Kopia 维护/DBR 流程回收，直接删 kopia 对象会破坏同 ns 其它备份。

**来源**
- [Migrating Applications — Veeam Kasten 文档](https://docs.kasten.io/latest/usage/migration/)（"Enable Backups via Snapshot Exports" / Export Location Profile / Export Snapshot References Only）
- [Backup Repository Configuration — Velero Docs](https://velero.io/docs/main/backup-repository-configuration/)（Kopia 仓库按 ns：`bucket/kopia/<ns>`）
